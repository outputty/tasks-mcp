# Reading state through a stale local copy answers for a world that has moved on

*PLANNING, 2026-08-26.*

## 1. The problem

This repository's MCP server is registered from its **local build**, not from npm:

```json
{ "mcpServers": { "tasks": { "command": "node", "args": ["dist/cli.js"] } } }
```

`dist/` is generated by `npm run build` (tsdown) and is **not** committed. So a session inspects
`src/` to reason about behaviour, and runs `dist/cli.js` to read state — two artefacts that agree only
as recently as the last build.

```
BEFORE
  git pull  ──►  src/ is new
  dist/     ──►  whatever the last local build produced
  session   ──►  reads src/, runs dist/   (assumes they match)
```

## 2. What was expected

That a read command reports the state the current code produces. A planning session opened on a branch
whose merges it had not built, ran `tasks-mcp planning` and `tasks-mcp roadmap`, and took both answers
as fact.

## 3. What actually happened

Both answers were produced by the previous build, and described a storage layout the merged code had
replaced.

The merged work changed how a project is identified — from a hashed path slug to a supplied, opaque id
— which changes which file a read opens. The stale `dist/` still used the old layout, found the old
cache file, and answered correctly *for code that was no longer there*:

```
$ node dist/cli.js planning          # stale dist
["tui-console-1787751801"]

$ npm run build && node dist/cli.js planning
[]
```

The empty answer was the true one: the identity cutover had orphaned this repository's own cache, and
nothing had rebuilt it yet. One `sync` restored 23 tasks under the new id — the free migration working
exactly as designed.

The cost was a wrong turn, not a wrong artefact. The stale reads looked healthy, so the session spent
its first probes chasing a discrepancy between two things that were never compared under the same code.
A second misreading followed immediately: with the rebuilt binary, `planning` returned `[]` and was
briefly read as a broken id round-trip, when the real cause was the session's own `start_task` having
taken the item out of the planning queue moments earlier.

## 4. Where it showed, and whether it repeats

1. `.mcp.json` — `node dist/cli.js`, deliberately, so the repository exercises the code in front of you
   rather than the last release. That choice is right and is what creates this trap.
2. `dist/` is in `.gitignore`, so `git pull` or a branch checkout **never** updates it. A merged change
   is invisible to every read until someone builds.
3. `npm run check` ends with `tsdown`, so a full check rebuilds — but a session that only reads state
   never runs it.
4. The failure is silent by construction: a stale binary does not error, it answers.

5. **It happened again the next day, through a different local copy.** A session opened knowing this
   lesson and rebuilt `dist/` as its first act — then read `roadmap` and got `tui-console 0/6` while
   `git log` showed all six layers merged. The binary was current; the **task cache** was not. Reads are
   answered by the local file layer and never hit the network, by design, so a build closing tasks in
   another process leaves this one's cache behind until something calls `sync`:

   ```
   $ node dist/cli.js roadmap     # fresh dist, stale cache
   tui-console-1787751801  open  0/6
   $ node dist/cli.js sync        # pulled: 29
   $ node dist/cli.js roadmap
   tui-console-1787751801  in_progress  6/8
   ```

6. **The same cause stalled the dispatcher, which is the expensive form.** A queue loop reported "no
   dispatchable target" three times in a row while a target with a ready task existed. Its reads came
   from an unsynced cache, so it held on an empty queue and announced that only a planning session could
   unblock it — when the work it was waiting for was already filed.

×2, and the second run is why the first one's rule was too narrow. It named `dist/` — a *build* artifact
— so a session could obey it in full and still be caught by the *data* cache next to it. Both are the
same thing: a local copy, read as if it were the truth.

## 5. How to prevent it

**Refresh every local copy before the first read, not just the build.** Two of them exist here and
both go stale silently:

```
npm run build                  # the CODE you read state through
node dist/cli.js sync          # the DATA that state is read from
```

`sync` is not optional housekeeping: reads are deliberately local and offline, so nothing in the tool
ever tells you the cache is behind. That is the designed trade, and it means the freshness step belongs
to the reader.

**For a dispatch loop, this is a correctness requirement rather than hygiene.** A loop that polls
`list_ready` without syncing can never see work another process filed, so it holds on an empty queue
forever and blames the absence of planning.

```
AFTER
  branch checkout / merge  ──►  npm run build  ──►  read state
```

And the general form, for any surprising read: **name the artefact that produced the answer, and check
its age against the source.** A read that disagrees with the code is a stale reader until proven
otherwise — that is a far commoner explanation than a bug in code that just passed CI.
